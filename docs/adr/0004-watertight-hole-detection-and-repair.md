# 0004: Watertight hole detection & repair - heuristic classification, positional hole ids, Blender subprocess reuse

Date: 2026-09-04

## Context

Beyond generating models and adjusting wall thickness, models (whether
generated by this service or uploaded) can have surface gaps that make
them unprintable - a couple of misaligned vertices leaving a small hole,
or a patch of faces with inverted winding ("wrinkle" defects that don't
show up in a shaded viewport but break slicer watertightness checks). Not
every open edge is a defect, though: a cup's mouth, an open box top, or
an open stand/base underside are all *deliberate* openings that must stay
open. `watertight.py` and `hole_classifier.py` implement finding these
regions and telling the two cases apart.

## Decisions

**Reuse the Blender-subprocess pattern from thickness.py**, rather than
inventing a new integration style: `watertight.py` mirrors
`_blender_binary_path()`/subprocess invocation/error handling, and the
actual bmesh work lives in `blender_scripts/` (analogous to
`thickness.py`'s inline script templates, but split into real files since
hole-detection needs substantially more logic - boundary-edge grouping,
Newell-method area/planarity, flipped-normal-island detection - than a
single Solidify-modifier call). `blender_scripts/close_holes.py` re-derives
the same hole ids `analyze_watertight.py` would report by sharing the
identical import/join/boundary-grouping code (`blender_scripts/_shared.py`)
- this determinism is what lets a hole id the caller saw in an analysis
response still mean the same boundary loop in a later repair call on the
same file. **Hole ids are therefore positional, not stable identifiers**:
they renumber whenever the file changes, including after a repair closes
some of them. `main.py`'s `/repair` route re-analyzes after every repair
so the job's cached hole ids stay consistent with the file's current state
- a caller that doesn't go through this API needs to re-analyze itself
before reusing an id.

**Classification is a hand-written geometric heuristic, not an ML/LLM
call** - deliberately, not just the simplest option. It's free to run (no
per-request cost, no Ollama/API backend dependency for this feature),
deterministic and unit-testable in milliseconds
(`tests/test_hole_classifier.py`), and its reasoning is directly
inspectable/tunable in code (size relative to the model, position
relative to the bounding box, planarity, boundary "raggedness" -
perimeter²/area vs. a circle) rather than opaque. The trade-off is
accuracy on unusual shapes the heuristic wasn't tuned for - mitigated by
always returning each hole's confidence and a human-readable reason
rather than auto-deciding, and keeping "close this one" a caller-driven
choice (the three.js viewer at `/watertight.html`) rather than something
this service does on its own.

One specific tuning note worth recording: on a **low-poly** model, a
couple of missing/stray triangles can still cover a surprisingly large
*fraction* of total surface area (there just isn't much area to begin
with), which can otherwise push the "size" signal toward "intentional".
`classify_hole()` in `hole_classifier.py` dampens this multiplicatively
with the boundary-raggedness signal rather than just averaging it in - a
real designed opening is almost always a clean, low-perimeter-for-its-area
shape, so a highly jagged boundary should heavily discount an otherwise
"big and cap-aligned" score, not just shave a fixed amount off it.

**Serve a web-viewable GLB alongside the JSON report, from the same
Blender invocation** (`--viewer-output` on both `analyze_watertight.py`
and `close_holes.py`), rather than a separate conversion call - halves
the Blender subprocess launches the viewer workflow needs.

## Bugs found and fixed during development (recorded here since they'd
otherwise be easy to reintroduce)

- **Blender/glTF axis mismatch.** The analysis JSON reports coordinates in
  the mesh's own (Blender, Z-up) space, but Blender's default glTF export
  converts to "+Y up" - empirically confirmed as
  `(x, y, z)_blender -> (x, z, -y)_gltf`. Every point/bbox from a report
  has to go through that same conversion (`pointToGltf`/`bboxToGltf` in
  `static/watertight.html`) before being placed in the three.js scene, or
  markers land nowhere near the actual mesh surface they're flagging.
- **OrbitControls singularity.** Camera auto-framing that points toward
  the average direction of flagged holes is undefined when that direction
  is parallel to the world "up" vector - e.g. a hole dead-center on a
  container's lid, an entirely ordinary case here. `frameCamera()` blends
  in a small horizontal nudge whenever the view direction is within ~10°
  of straight up/down.
- **Multi-user mesh data on transform_apply.** A freshly-imported mesh
  object's data-block can come back `users > 1` (Blender's own undo/orphan
  bookkeeping) even with only one object in the scene;
  `bpy.ops.object.transform_apply()` refuses to run on multi-user data.
  `_shared.join_into_single_object()` force-copies the data first.
- **numpy needed for glTF export on the Debian `blender` apt package.**
  See `TROUBLESHOOTING.md` and the Dockerfile's `python3-numpy` line -
  `thickness.py` never hit this because its Solidify path only exports
  STL, never glTF.

## Related: three.js is vendored locally, not loaded from a CDN

`static/vendor/three/` holds the exact three.js files `static/index.html`
and `static/watertight.html` import (r0.160.0, MIT-licensed), matching
`index.html`'s own existing "no build step, no external scripts/CDNs"
principle (Docker-first, works fully offline once the container is up) -
this wasn't a new precedent, just extending one already set.
